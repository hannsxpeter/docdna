## Findings

### MEDIUM-001: Release installation is not bound to verifiable provenance

- **Category**: OWASP A03:2025 Software Supply Chain Failures
- **Location**: `README.md:54-60`, `.github/workflows/ci.yml:14-18`, `.github/workflows/ci.yml:162-168`, `install.sh:17-47`
- **Description**: Installation copies whatever bytes are present in a checkout selected by the documented
  `v1.4.0` tag. The repository does not publish or verify a release checksum, signature, artifact
  attestation, or provenance statement. CI pins action code and limits token permissions, but its runner,
  latest Python lane, and apt package are mutable. The tag was not present in this pre-publication checkout.
- **Impact**: A compromised upstream release identity, moved tag, substituted archive, or compromised mutable
  CI input can place altered Python and agent instructions into a user's coding-agent skill directory without
  an independent byte-level trust check.
- **Reproduction**: Run the A03 procedure. Confirm that action pins are full commits, then observe that tag
  verification and integrity-artifact discovery cannot establish a signed or hash-bound release identity.
- **Observed Result**: `git tag -v v1.4.0` returned exit 1 because the pre-publication tag was absent; integrity
  artifact discovery returned no matches; mutable runner and package inputs remained.
- **Evidence**: A03 coverage row and procedure; `README.md:57`; `.github/workflows/ci.yml:14-18`;
  `.github/workflows/ci.yml:162-168`.
- **Reviewed At**: 2026-08-19T12:07:07Z
- **Owner**: Release owner
- **Target**: 2026-09-02
- **Remediation Options**:
  - **Option A**: Publish release archives with SHA-256 sums plus Sigstore or equivalent signatures and make
    installation verify them before executing or copying source. Estimated: 2 days.
  - **Option B**: Document installation by full commit ID, create a signed annotated release tag, pin the CI
    runner and ShellCheck source where practical, and publish SLSA-style provenance for the released tree.
    Estimated: 3 days.
- **Status**: Open

### MEDIUM-002: Installed runtime and proof bytes are not authenticated

- **Category**: OWASP A08:2025 Software or Data Integrity Failures
- **Location**: `skill/scripts/docdna_doctor.py:89-131`, `skill/scripts/docdna_doctor.py:157-228`,
  `skill/scripts/docdna_runtime.py:607-713`, `skill/scripts/docdna_proof.py:330-436`
- **Description**: Doctor checks resource presence, safe file shape, size, Python syntax, and registry schema,
  but it has no trusted manifest of expected member digests. Installed Proof validates claim structure and
  intentionally skips checkout-only evidence and replay. A valid-code change or valid-schema claim change
  therefore remains a passing installed health result.
- **Impact**: Same-user tampering, a compromised updater, or post-distribution file replacement can change
  executable skill behavior or agent-facing proof claims without Doctor or installed Proof detecting that the
  bytes differ from the reviewed release.
- **Reproduction**: Run the A08 procedure against an isolated copy. Change the Scan version string without
  breaking syntax, then replace one proof claim with a valid string and rerun both commands.
- **Observed Result**: Doctor passed 4 of 4 checks before and after the runtime change. Installed Proof passed
  and rendered the tampered claim.
- **Evidence**: A08 coverage row and procedure; retained probe layout
  `/tmp/docdna-harden-tamper.x3Jq5M`; the cited validator implementations.
- **Reviewed At**: 2026-08-19T12:07:07Z
- **Owner**: Runtime maintainer
- **Target**: 2026-09-02
- **Remediation Options**:
  - **Option A**: Ship a signed release manifest containing every installed member path and digest; have Doctor
    verify it against a separately trusted release identity. Estimated: 3 days.
  - **Option B**: Bind a generated digest manifest to the verified release artifact from MEDIUM-001, compare
    every registered resource, and report structural-only versus authenticated health as distinct verdicts.
    Estimated: 2 days after MEDIUM-001.
- **Status**: Open

### MEDIUM-003: Installer failure can destroy the last working install

- **Category**: OWASP A10:2025 Mishandling of Exceptional Conditions
- **Location**: `install.sh:40-49`
- **Description**: `install_skill` recursively removes the destination, recreates it, and then copies the new
  tree in place. There is no staging directory, pre-promotion validation, atomic directory swap, backup, or
  rollback if copy, permission changes, interruption, or storage exhaustion occurs.
- **Impact**: A routine upgrade failure can remove a working DocDNA skill and leave a missing or mixed runtime.
  The host may stop loading the skill or may load only part of its commands and agent instructions until the
  user notices and reinstalls.
- **Reproduction**: Run the A10 procedure with a temporary destination and a failing `cp` shim. The sentinel
  represents the previous working install.
- **Observed Result**: Installer returned exit 1, removed the sentinel, and left an empty destination.
- **Evidence**: A10 coverage row and procedure; retained probe layout
  `/tmp/docdna-harden-install.hWOFcy`; `install.sh:45-49`.
- **Reviewed At**: 2026-08-19T12:07:07Z
- **Owner**: Installer maintainer
- **Target**: 2026-09-02
- **Remediation Options**:
  - **Option A**: Copy into a sibling staging directory, run Doctor there, then atomically promote it while
    retaining the prior directory until success. Estimated: 2 days.
  - **Option B**: Move the prior install to a recoverable backup, install and validate the replacement, restore
    the backup on every failure or signal, and test copy, chmod, and interruption faults. Estimated: 2 days.
- **Status**: Open
