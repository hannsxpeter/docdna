# How it decides

The selection engine is the product. Everything else in docdna exists to feed it or to report what it
concluded. This page is the technical account: what goes in, how the decision is made, what comes out, and
where the boundaries are.

If you want the plain-language version first, read [QUICKSTART.md](QUICKSTART.md) instead.

## The inputs

Three things go in, and no more.

**Signals.** 132 facts read out of the repository, defined in `skill/catalog/signals.json`. Each comes back
present, absent, or unknown. A present signal carries evidence: the files that made it true.

**An archetype.** What kind of project this is. Eight primaries (client application, commercial SaaS, data
platform, embedded device, internal service, open-source library, research artifact, solo utility) scored
against the signals, plus ten overlays for characteristics layered on top (agent skill package, AI system,
app store, health, operated by others, payments, public UI, regulated, safety critical, shipped artifact).
Below a scoring floor the archetype resolves to `unknown` and the interview becomes mandatory rather than
optional.

**Up to eight interview answers**, of which **none is asked on the first run**. Every one is defaulted from
signals, labelled `assumed`, and printed with its blast radius, so the user corrects in a sentence instead
of completing a form.

## The eight questions

| Id | What it settles |
| --- | --- |
| `q1_users` | Who can see and use this: private, internal, or public |
| `q2_operator` | Who runs it in production, if anyone does |
| `q3_authorizer` | Whether an external body can audit or authorize this |
| `q4_decides_about_people` | Whether the system makes decisions about individuals |
| `q5_markets` | Which markets or jurisdictions it serves |
| `q6_downtime` | What an outage costs |
| `q7_maintenance` | The maintenance commitment being made |
| `q8_doc_location` | Whether documentation lives somewhere other than this repository |

`q3_authorizer` and `q5_markets` carry the most weight, because between them they decide whether a
regulatory relationship exists. `q4_decides_about_people` is the one question that may never be defaulted
from a signal, enforced as invariant I5, because inferring from code that a system makes decisions about
people is not a guess the tool is entitled to make.

## What "decides" actually means

Be precise about the scope of the claim, because an earlier version of this documentation was not.

The registry holds 132 signals. Across the 51 repositories measured in [MEASUREMENT.md](MEASUREMENT.md),
the count coming back present ranged from 4 to 46, with a median of 19. How many come back `unknown` has
never been measured across a corpus, and no median for it is published anywhere.

So the honest description is not that docdna decides your documentation set. **It decides what the code can
settle, and it shows you what it assumed about the rest.** Any narration stronger than that is an
overclaim.

## Absence of evidence is never encoded as false

This is the load-bearing rule of the whole design.

A detector that did not run reports `unknown`. A detector that ran and refused to guess reports `unknown`.
And `unknown` never silences a document. There is no path by which "we did not look" becomes "this does not
apply".

Every unknown is printed, grouped by signal family. A family the scanner refused to guess at names the
question that would resolve it. A family whose gate never fired sometimes names a resolving question and
sometimes names none, because a pass that never ran can leave nothing to ask about. The
[README](../README.md#the-part-that-earns-your-trust) carries that section of real output, regenerated by
the test suite.

## Every selection names what selected it

A selected document always says why it was selected. There are four possible answers, and they are not
interchangeable:

1. **A signal.** The row cites the signal and the file that carries it. This is the case with a path you
   can go and look at.
2. **The catalog baseline.** The catalog selects this document for every repository, `govern.manifest` being
   the obvious one.
3. **An interview answer.** Including a defaulted, assumed one.
4. **A signal's absence.** The document is owed precisely because something is not there.

Only the first has a file path to give, because the other three are not places in the code. On this
repository's own manifest, 13 of 48 selected rows fall into the last three groups. A row naming no signal is
not thereby unrequired: `govern.manifest` is required and cites no signal at all.

## Every exclusion carries three things

An unexplained exclusion is worse than a missing document, because it launders a gap into a decision. So
every excluded row carries:

- a **reason**, in prose, that a human can disagree with
- a **citation**, so the reason can be checked
- a **`revisit_when` tripwire**, a predicate that makes the exclusion expire

The tripwire is what stops the ledger from rotting. A document correctly skipped last quarter reports
itself the moment the signal that justified skipping it stops being true.

What is known about tripwires firing, stated carefully: firing is observed on a real repository. Run
`docdna_check.py` against this one and `govern.ownership` fires. But every firing observed so far, here and
in the tests, is a **first evaluation**, where the predicate was already true the moment it was first
checked. The temporal case the feature actually rests on, an exclusion written while its predicate was false
and a later run catching it after the repository changed, has not been observed. That is the claim to hold
open.

## The catalog

96 entries in `skill/catalog/documents.json`, organized by **lifecycle stage**, not by audience.

Audience is not a valid partition. The CTO's architecture view and the engineer's architecture view are one
artifact at two zoom levels, and tiering documents by reader guarantees four parallel document sets that
drift apart. The ten stages are `frame`, `decide`, `design`, `build`, `verify`, `assure`, `operate`,
`serve`, `govern`, and `retire`.

Each entry declares how far docdna can go:

| `producible` | Count | Meaning |
| --- | --- | --- |
| `Y` | 42 | docdna can write it from code evidence |
| `M` | 37 | Manifest only. docdna tracks the row, names what selected it, and states what a human must supply |
| `R` | 17 | Refused. docdna will never write it, and says who has to sign it |

The `M` tier is where the threat model, the runbook, the access control inventory, and the data
classification register live. The `R` tier is covered in [COMPLIANCE.md](COMPLIANCE.md).

## Ten invariants, enforced at load time

The catalog rules are checked when the catalog loads, so a change that violates one fails the build instead
of degrading quietly. The full list is normative in
[../skill/catalog/SCHEMA.md](../skill/catalog/SCHEMA.md); the two that matter most to how selection behaves:

- **I6: no signal alone may make a legal instrument required.** A grep that finds an IAM role must not make
  a System Security Plan mandatory. Only an interview answer can raise a refused entry to required.
- **I4: a jurisdiction hint may open a question, never set a verdict.** A stray `eu-west-1` in a Terraform
  file must not make a GDPR processing record required. This is checked semantically, refusing every path
  from a jurisdiction hint to a verdict, rather than by matching the syntax of one.

## The boundary

docdna sees documentation committed to the repository it is pointed at. That is the whole visible surface.

It says so in every report, unprompted, because reporting "absent" for a document that lives in a wiki costs
the reader's trust in every other row. If your documentation lives in Confluence, SharePoint, or Notion, say
so and those rows are marked present elsewhere rather than missing.

A repository that vendors another repository (fixtures, examples, a bundled dependency) would otherwise have
that project's documentation and manifests read as its own, against the wrong root. Name those directories
with `--exclude-dir`, or as `exclude_dirs` in `.docdna/config.json`.
