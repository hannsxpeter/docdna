# Getting started

A guided first run, written for somebody who has not seen this tool before and does not want to read the
source to use it. No prior setup, no configuration file, no questions to answer.

## What you need

Python 3.8 or newer on a POSIX host with descriptor-relative, no-follow filesystem support, and a coding
assistant that supports skills (Claude Code, Codex, Cursor, or Windsurf). Windows is not supported. There
is no third-party Python package to install, no account to create, no service to reach, and nothing leaves
your machine.

Check your Python:

```sh
python3 --version
```

## Install it

```sh
git clone --branch v1.3.0 --depth 1 https://github.com/hannsxpeter/docdna.git
cd docdna
./install.sh claude
```

Swap `claude` for `codex`, `cursor`, `windsurf`, or `all`. Then restart your assistant, because skills are
read when it starts up.

If you want to know exactly where files landed, that is in [AGENT_SUPPORT.md](AGENT_SUPPORT.md).

## Your first run

Open your assistant in the project you care about and ask, in your own words:

> survey the documentation for this repo

Things worth knowing before you do:

- **It asks you nothing.** Every judgment call is made from the code, labelled as an assumption, and shown
  to you with the cost of being wrong attached.
- **It writes no project documentation.** A survey reads the repository and writes its report and
  machine-readable ledger. When existing documents are worth indexing for an agent, it also writes the
  index and its metadata sidecar.
- **It does not touch your code.** Ever, in any mode.
- **It leaves two core files behind.** `DOCDNA.md` is the one-screen summary meant for humans, and
  `.docdna/manifest.json` is the complete ledger meant for tools. A run that emits the agent index also
  leaves `llms.txt` and `.docdna/meta/build.llms-txt.yml`.

A real, unedited survey report is in the [README](../README.md#what-a-first-run-looks-like), annotated line
by line. It is regenerated by the test suite, so what you see there is what the tool prints.

## Reading the report

The report is one screen with named blocks. In the order they appear:

| Block | What it is telling you |
| --- | --- |
| The first line | What docdna worked out about your project unaided: its kind, size, licence, and how it builds |
| A coverage count | How many of the documents it thinks you owe are actually present |
| **Missing and load-bearing** | The short list that matters. Each row names the document and the file in your code that put it on the list |
| **Not applicable** | A count of documents ruled out, plus any that are one answer away from becoming relevant |
| **Note** | The boundary. docdna only sees documentation committed to this repository |
| **Assumed** | Every guess it made, in one place, with what changes if a guess is wrong |
| **Possible stale references** | Places a document and the code look like they disagree. Leads for a human, not verdicts |
| **Next** | Two or three concrete things you could do now |

You will never be shown the full list of ruled-out documents in the report. A hundred-row annotated list of
everything you do not have is exactly the theatre this tool exists to prevent. It is all in
`.docdna/manifest.json` if you want it.

## Correcting an assumption

The **Assumed** block is the one to read twice. It might say, for example, that it assumed nothing external
audits this project and nothing is deployed anywhere. If that is wrong, one sentence fixes it. Tell your
assistant, or run:

```sh
python3 skill/scripts/docdna_select.py --answer q2_operator=separate-ops-team .
```

There are eight questions in total and you will never be asked all of them. Each one, when answered, can
move a group of documents in or out. The eight are described in
[HOW-IT-DECIDES.md](HOW-IT-DECIDES.md#the-eight-questions).

## Getting documents written

Once you are happy with the picture, ask for the writing pass:

> backfill the docs

It defaults to ten documents that are read straight off the code, so they carry almost no risk of being
made up. It will estimate the work before it starts, cap itself at five documents per run, and pick up
where it left off if something interrupts it.

If you already know what you want, say so directly:

> write the config reference for this repo

That skips straight to writing that one document. Being told exactly what to do should never be answered
with a questionnaire.

Every document arrives with citations on its claims and clearly marked gaps where a human has to decide
something. **A gap is not a failure.** It is the tool refusing to invent your recovery time objective.

## Keeping it honest over time

The third mode re-checks documents against the code, and is the one to put in continuous integration:

> check the docs against the code

Drift warns unless you choose a small assurance set, usually three to five documents. The prose pass also
warns about literal editorial patterns, but it never gates or rewrites a document:

```sh
python3 skill/scripts/docdna_check.py --only prose .
```

Unicode hygiene is also included. Terminal controls, bidirectional controls, and Unicode tag characters
fail at the default `major` threshold, while other invisible format characters warn. Inspect that pass
alone with:

```sh
python3 skill/scripts/docdna_check.py --only hygiene .
```

It reports exact codepoints and locations but never rewrites your documents. Only DocDNA's generated
human-facing prose is cleaned before writing. Statistical text watermarks and file metadata are outside
this check.

## Glossary

The report uses a handful of terms with specific meanings.

**Signal.** One fact read out of your code. "This project exposes HTTP routes." "There is a CI workflow."
There are 132 of them. A signal comes back present, absent, or unknown.

**Unknown.** docdna looked and could not tell, or deliberately declined to guess. Unknown is never treated
as "no", and unknown never rules a document out. This distinction is why the ledger is worth showing to an
assessor.

**Archetype.** What kind of project this is: an open-source library, an internal service, a commercial
product, and so on. Eight main kinds, plus ten overlays for things layered on top, such as handling
payments or health data.

**Catalog.** The list of 96 documents docdna knows about, and the rules for when each one applies.

**Selected.** A document this project owes. Every selected document names what selected it.

**Excluded, or not applicable.** A document this project does not owe. Every exclusion carries a reason, a
citation, and a tripwire.

**Tripwire.** An expiry condition attached to an exclusion. A document correctly skipped last quarter
reports itself the moment the thing that justified skipping it stops being true.

**Manifest.** The complete machine-readable ledger at `.docdna/manifest.json`. Every document, selected or
not, with its reasoning.

**Citation.** A pointer from a sentence in a generated document to the place in your code that proves it.

**Gap.** A marked hole in a generated document where a human decision is required. Deliberate, visible, and
counted.

**Drift lead.** A place where a document and the code appear to disagree. A lead, not a finding. Their
measured accuracy is published in [MEASUREMENT.md](MEASUREMENT.md).
